# Legacy data migration (old Supabase project "LF Creative" -> Gear Tracker)

One-off, repeatable import of the old inventory data. Code: `scripts/legacy/`. **Nothing here was run against the real
legacy data**; it is built and tested on a hand-made fixture with the shapes and counts from the brief
(see "What is and is not verified").

## Security boundary
- The cloud session never holds credentials for the old database. **You** run `schema-probe.sql` and `export.sql`.
- `inventory_team_members` (PINs, passwords) is **never exported or migrated**; re-invite people through Supabase Auth.
  Not exported either: `inventory_employee_settings`, sessions (transient), job tables (empty).
- `export.sql` stops if any exported table has a credential-like column, and the importer refuses any file that has one.
- The importer refuses to write into the legacy project (`vxgtywdqijtfnkgyubkh`).
- The exported JSON and reports contain inventory data: they are gitignored (`scripts/legacy/export/`); keep them off GitHub.

## Runbook (you run these)
From `scripts/legacy` (`npm ci` once).

1. **Look at the real columns first** (read-only, reads no rows):
   `psql "$LEGACY_DATABASE_URL" -X -f schema-probe.sql`
   Compare with "Assumed legacy columns" below. If a name differs, write a `columns.json` override (example below).
2. **Export** (read-only transaction, rolled back):
   `mkdir -p export && psql "$LEGACY_DATABASE_URL" -X -v ON_ERROR_STOP=1 -f export.sql`
3. **Check the export without any database:**
   `npm run import -- --export-dir export --plan-only --report-dir report [--columns columns.json]`
   A wrong column name stops here with the list of columns that do exist. Read `report/reconciliation.md`.
4. **Approve the decisions** in the report: location kinds (override with `--kinds kinds.json`), probable duplicates,
   unresolved references (see "Open questions the report answers").
5. **Dry run** against a throwaway database first (`supabase start`, then `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres`):
   `npm run import -- --export-dir export --dry-run --report-dir report` — everything runs inside one transaction and is
   **rolled back**; the report includes the checks against the database.
6. **Commit** to staging, then production, using a database owner connection (not an API key):
   `DATABASE_URL=... npm run import -- --export-dir export --commit --report-dir report`
   It commits only if every check passes; otherwise it rolls back and exits 1. Exit codes: 0 ok, 1 checks failed, 2 bad input.
7. **Afterwards:** re-invite users (Auth), promote the first admin, fix "Other" categories and missing types in the web app,
   review probable duplicates, decide what to do with photos (see below), print new labels only when you want to (old labels keep working).

`columns.json` / `kinds.json` examples:
```json
{ "assets": { "tag": "asset_tag", "containerRef": "container_uuid" }, "events": { "performer": "user_name" } }
```
```json
{ "10112": "cabinet", "loc-sav": "site" }
```

## What is imported
| Legacy | New | Notes |
|---|---|---|
| `inventory_assets` | `assets` | category + type + size + cost + notes + serial + photo URLs; legacy id and tag kept in `custom` |
| `inventory_containers` | `assets` with `is_container` | category "Cases & Bags" |
| `inventory_locations` | `locations` (+ tag for the code) | parents first; kinds proposed (see below) |
| `inventory_events` / `inventory_container_events` | `asset_events` | original timestamps; performer name in `payload.legacy_performer` |
| `asset_id` / `container_id` / location `code` | `tags` | NFC dash-hex -> uppercase hex `nfc`; everything else `barcode` |
| checked-out status | open `checkouts` + `checkout_items` | see below |
| `inventory_audits` / `inventory_audit_items` | `audits` / `audit_lines` | results mapped found / missing / unexpected |
| all of the above | `legacy_id_map` | legacy row -> new row, for traceability (admin-readable only) |

New `asset_code`s (A000001..., C000001...) are generated by the database in a stable order (containers, then assets, each by
creation time). Every imported row has a **deterministic id** (UUIDv5 of legacy table + id), which is what makes re-runs safe.

## Mapping decisions (change with the engineer, not silently)
- **Tags / old labels.** Dash-separated hex pairs (`04-46-88-0A-BF-2A-81`) become uppercase hex NFC tags; plain numeric
  codes stay barcodes. The app resolves both spellings, so old labels keep scanning. A value too short to be an NFC UID stays a
  barcode (warned). Two rows with the same tag: the first keeps it, the second is reported (`tag_collision`), its asset is still imported.
- **Placement.** `container_id` -> `parent_asset_id`; else `current_location_id` -> `parent_location_id`. An asset has at most one
  parent: if both are set the container wins and it is reported (`both_parents`). A container reference that is missing, or points at an
  asset that is not a container, falls back to the location (`orphan_container_ref`, `parent_not_container`).
- **Location kinds (proposal, needs approval).** roots = `site`; name starts with "Storage" = `cabinet`; name starts with "Tray" = `bin`;
  other direct children of a site = `room`; anything else = `other`. The report lists every location with its proposed kind.
  `linked_asset_id` is not imported; each one is listed (`location_linked_asset`).
- **Categories.** `category` -> category (empty -> "Other"); `type` -> `custom.legacy_type`. "Other" and missing types are listed for clean-up.
- **Status.** available / checked_out (also "out", "rented") / in_repair (also "repair", "maintenance") / lost / retired. Unknown values
  import as available and are reported.
- **Checked-out assets.** One open checkout per (renter, due date), reason `Legacy import: <renter>`, one line per asset. Due date =
  `rental_due_date`, else `expected_return_date`, else none (reported). A bare date means the **end of that day (UTC)**. The checkout date is
  the asset's latest checkout event, else a fallback (reported). A container's checkout is **not** cascaded to its contents.
- **Last seen.** `last_known_lat/lng/at` -> `last_seen_*`.
- **Events.** `created`->created, `checkin`->checked_in, `checkout`->checked_out, `edited`->edited. `location` -> `placed_in_location` when a
  location is known, otherwise `seen` (with the GPS point if any). `inquiry` -> `seen` with `payload.legacy_inquiry = true`.
  Container events: `asset_added`->placed_in_container, `asset_removed`->removed_from_container, `location_update`->placed_in_location,
  `check_out`/`check_in`->checked_out/checked_in, `created`->created. Events with an unknown asset (`orphan_event`), no usable time, or an unmapped type are skipped and listed.
  Events are written directly (nothing is replayed), so they never change current state; the state comes from the imported snapshot.
- **Probable duplicates.** Bag / Hard Case / case-like assets with the same name or tag as a container are **listed, never merged**.
- **Photos.** `photo_urls` are kept in `custom.legacy_photo_urls` and listed in the JSON report; nothing is downloaded or copied
  (the Storage bucket does not exist yet). Decide later whether the old URLs are still fetchable.

## Assumed legacy columns
Not known to the author; inferred from the brief. Check them with `schema-probe.sql`; the importer **stops** (listing the columns that do exist) if a required one is missing.
`inventory_assets`: `id`, `asset_id` (the tag text), `name`, `status`, `category`, `type`, `size`, `cost`, `notes`, `serial_number`, `photo_urls`, `container_id`, `current_location_id`, `last_known_lat`, `last_known_lng`, `last_known_at`, `renter`, `rental_due_date`, `expected_return_date`, `created_at`.
`inventory_containers`: `id`, `container_id` (tag text), `name`, `status`, `notes`, `current_location_id`, `renter`, `rental_due_date`, `expected_return_date`, `created_at`.
`inventory_locations`: `id`, `code`, `name`, `parent_id`, `kind`, `linked_asset_id`.
`inventory_events`: `id`, `asset_id`, `event_type`, `created_at`, `performed_by`, `location_id`, `gps_lat`, `gps_lng`, `notes`.
`inventory_container_events`: `id`, `container_id`, `asset_id`, `event_type`, `created_at`, `performed_by`, `location_id`, `notes`.
`inventory_audits`: `id`, `location_id`, `started_at`, `finished_at`. `inventory_audit_items`: `id`, `audit_id`, `asset_id`, `status`.
Required (import stops without them) are listed in `REQUIRED` in `scripts/legacy/src/types.ts`; everything else is optional and reported if absent.

## Open questions the report answers (do not guess; read the report)
- **Does `inventory_assets.container_id` reference `inventory_containers.id` or `.container_id` (the tag)?** The importer tries both, and the report
  shows how many references resolved each way (`container_id on assets: {...}`). Events and audits are resolved the same way (`asset references`).
- Which Bag / Hard Case assets duplicate a container (`Probable duplicates`).
- Whether any asset's container is not in `inventory_containers` (`parent_not_container`).

## Idempotency
Re-running is safe: every insert is `ON CONFLICT DO NOTHING` on a deterministic id, so a second run adds only what is missing and
**does not overwrite edits made in the new system** (the report counts "pre-existing rows that differ from legacy" as information, not failure).
Placement is only set for rows created by that run.

## Reconciliation report
Written to stdout and, with `--report-dir`, `reconciliation.md` + `.json`. Contents: rows in vs imported per table (with skipped counts),
a read-back from the database compared with the legacy snapshot (assets present, **assets by status**, **contents of every container**,
**placement and effective location of every asset**, open checkout lines, tags, locations, events by type, audits), every issue grouped by
code with examples, how references were resolved, duplicates, photos, clean-up needed, and the location-kind proposal.
`--plan-only` prints the same report without any database and says **NOT CHECKED** (it cannot pass).

## What is and is not verified
Verified (automated, `scripts/legacy`: 54 unit tests + 10 integration tests against a real PostgreSQL with the project's migrations and seed;
CI runs them against `supabase start`): the mapping rules, ids, tag normalisation, credential guard, column validation, dry-run rolls back
and leaves nothing behind, a committed import matches the legacy snapshot (status, containers, placement, effective location, checkouts, events),
re-running adds nothing and keeps later edits, a code clash is reported and fails safe, `export.sql` against a look-alike database
(valid JSON, special characters survive, credential columns stop it).

**Not verified:** anything against the real legacy data or schema. The column names above are assumptions, the real data will contain cases
the fixture does not, and `export.sql` has not run on the real database. Treat the first real `--plan-only` and `--dry-run` as the real test.
